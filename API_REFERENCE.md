## 4. Структура і призначення файлів

| Папка або файл | Призначення |
|---|---|
| `run.py` | Запускає сервер на локальному порту |
| `app/__init__.py` | Створює Flask-застосунок і налаштовує відповіді на помилки |
| `app/config.py` | Зчитує параметри підключення з `.env` |
| `app/db.py` | Відкриває з’єднання з MySQL на час запиту та закриває його |
| `app/controller/api.py` | Приймає HTTP-запити, читає JSON і повертає відповіді |
| `app/service/crud_service.py` | Перевіряє дані та виконує сценарії створення, читання, зміни й видалення |
| `app/service/relation_service.py` | Формує відповіді для пов’язаних сутностей |
| `app/dao/base_dao.py` | Виконує SQL для CRUD; значення передає через параметри `%s` |
| `app/dao/relation_dao.py` | Виконує JOIN-запити через проміжну таблицю |
| `app/domain/schema.py` | Описує 11 дозволених сутностей, їхні поля, ключі та зв’язки |
| `app/dto/record_dto.py` | Перетворює записи в JSON-сумісні DTO |
| `postman/Kindergarten_Lab4.postman_collection.json` | Готові 79 запитів із перевірками відповідей |
| `tests/` | Перевірки валідації й інтеграційні тести з окремою тимчасовою базою |

Шлях запиту: **Postman → Controller → Service → DAO → MySQL → DTO → JSON-відповідь**.

Спільний `BaseDAO` і `CrudService` використовуються для всіх таблиць, щоб не повторювати однакові функції 11 разів. Для кожної сутності контролер реєструє окремі URL. Усі SQL-операції виконуються в DAO, перевірки даних — у сервісі, форматування відповіді — у DTO.

## 5. CRUD для всіх таблиць

Замість `{table}` підстав одну з назв: `addresses`, `kindergartens`, `positions`, `employees`, `employment_history`, `salary_payments`, `bonus_payments`, `child_groups`, `children`, `group_enrollments`.

| Метод і адреса | Дія | Успішна відповідь |
|---|---|---|
| `GET /api/{table}` | Переглянути всі записи | 200, список `data` та `count` |
| `GET /api/{table}/{id}` | Переглянути один запис | 200, об’єкт `data` |
| `POST /api/{table}` | Додати запис із JSON у Body | 201, створений запис і заголовок Location |
| `PUT /api/{table}/{id}` | Замінити дані запису | 200, оновлений запис |
| `DELETE /api/{table}/{id}` | Видалити запис | 204, порожнє тіло |

Для `employee_groups` складений ключ із двох чисел:

```text
GET    /api/employee_groups
POST   /api/employee_groups
GET    /api/employee_groups/1/2
PUT    /api/employee_groups/1/2
DELETE /api/employee_groups/1/2
```

`1/2` означає пару `employee_id=1, group_id=2`, а не номер рядка.

У POST не передавай автоматичний первинний ключ. MySQL створить його сам. Виняток — `employee_groups`, де обидва ключі задаються вручну.

PUT передає всі обов’язкові поля запису. Пропущені необов’язкові поля стають `null`. Автоматичний первинний ключ через PUT не змінюється. Для `employee_groups` у PUT можна замінити пару ключів, якщо нова пара ще не існує.

## 6. Приклад вручну в Postman

Спочатку GET:

```text
http://127.0.0.1:5001/api/children
```

Потім обери метод POST, ту саму адресу, **Body → raw → JSON** і встав:

```json
{
  "last_name": "Тестенко",
  "first_name": "Марія",
  "middle_name": null,
  "birth_date": "2022-05-10"
}
```

Натисни Send. З відповіді візьми `child_id`. Наприклад, якщо повернулося `child_id: 11`, адреса одного запису — `/api/children/11`. Використовуй фактичний отриманий ID.

Для PUT на цю адресу передай:

```json
{
  "last_name": "Тестенко",
  "first_name": "Софія",
  "middle_name": "Іванівна",
  "birth_date": "2022-05-10"
}
```

Потім зроби GET цього ID для перевірки, DELETE цього ID для видалення й повторний GET — він має повернути 404.

## 7. Зв’язки 1:M і M:M

### 1:M

Методичка називає перевірку «зі сторони M:1»: отримати всіх дочірніх суб’єктів для одного батьківського. Наприклад, усі групи одного дитсадка:

```text
GET /api/kindergartens/1/child_groups
```

Також реалізовані:

```text
GET /api/addresses/1/kindergartens
GET /api/kindergartens/1/employment_history
GET /api/employees/1/employment_history
GET /api/positions/1/employment_history
GET /api/employment_history/1/salary_payments
GET /api/employment_history/1/bonus_payments
GET /api/children/1/group_enrollments
GET /api/child_groups/1/group_enrollments
```

Спочатку перевіряється існування батьківського запису. Для існуючого батька без дочірніх записів повертається `data: []`, `count: 0`; для неіснуючого — 404.

### M:M

Один працівник може працювати з кількома групами; з однією групою можуть працювати кілька працівників. Зв’язок збережений у `employee_groups`.

```text
GET /api/employees/1/groups
GET /api/child_groups/1/employees
GET /api/relations/employees_groups
```

Перший запит повертає всі групи працівника №1 через JOIN зі стикувальною таблицею. Другий — усіх працівників групи №1. Третій — усіх працівників, у кожного з яких вкладений список `groups`. Працівники без призначень теж повертаються, зі списком `groups: []`.

Додати зв’язок:

```text
POST /api/employee_groups
```

```json
{"employee_id": 1, "group_id": 3}
```

Видалити саме цей зв’язок: `DELETE /api/employee_groups/1/3`. Це не видаляє самого працівника чи групу.

## 8. Автоматичний прогін у Postman

1. Запусти Python-сервер і перевір `/api/health`.
2. У Postman натисни **Import → Files** та обери `postman/Kindergarten_Lab4.postman_collection.json`.
3. Відкрий імпортовану колекцію. Змінна `base_url` уже має значення `http://127.0.0.1:5001`.
4. Натисни **Run collection** і виконай усі папки зверху вниз, одну ітерацію.
5. Перевір результати Tests. В окремих запитах навмисно очікуються 400, 404 і 409 — це успішна перевірка обробки помилок.

Колекція спочатку читає таблиці, потім створює власні записи у правильному порядку, запам’ятовує їхні ID, перевіряє читання/оновлення/зв’язки, а в кінці видаляє лише створені записи у зворотному порядку залежностей. Запускай усю колекцію, щоб змінні ID були актуальними. Якщо перервеш її посередині, створені тестові рядки можуть залишитися в базі; повторний повний прогін використовує новий набір ID і нову унікальну назву посади.

## 9. Валідація та коди відповідей

- Перевіряються обов’язкові поля, типи, довжина тексту, коректність дат та невід’ємні суми з максимум двома знаками після крапки.
- `age_min` не може перевищувати `age_max`; місткість має бути додатною.
- Дата звільнення/вибуття не може передувати даті прийняття/зарахування; дата народження не може бути майбутньою.
- Неіснуючі зовнішні ключі й повторення унікальних значень відхиляє MySQL; API повертає зрозумілий JSON із кодом 409.
- Батьківський запис, який використовується в інших таблицях, не видаляється: спочатку потрібно видалити залежні записи.
- 400 — некоректні дані, 404 — запис або маршрут відсутній, 415 — тіло запиту не JSON, 503 — немає підключення до MySQL.

Дати у відповідях мають формат `YYYY-MM-DD`. Суми повертаються текстом, наприклад `"18000.50"`, щоб зберегти точність DECIMAL. API допускає суму в JSON як число або текст.

Перевірка перетинів періодів зарахування, перевищення фактичної кількості дітей над місткістю та відповідності віку дитини групі не реалізована. Ця робота реалізує CRUD і зв’язки на основі наявної моделі, а не повну систему обліку дитсадка.

## 10. Що змінилося після третьої роботи

У третій роботі ти створював таблиці та виконував SQL вручну у Workbench. У четвертій між клієнтом і MySQL з’явився Python-сервер. Postman надсилає йому HTTP-запит, контролер викликає сервіс, сервіс перевіряє дані й звертається до DAO, DAO виконує SQL. Результат перетворюється на DTO і повертається як JSON.

Структура таблиць та нормальні форми залишилися ті самі. Нові частини роботи — HTTP, REST CRUD, шари програми, DTO, параметризовані SQL-запити, обробка помилок і перевірка через Postman.

Коротко для захисту:

> Я реалізував Flask-сервер для бази «Дитсадок», варіант 34. Для всіх 11 таблиць доступні створення, читання, оновлення та видалення. Контролери обробляють HTTP-запити, сервіси перевіряють дані, DAO виконують SQL, а DTO формують JSON-відповіді. Реалізовано перегляд дочірніх записів для зв’язків один до багатьох і вибірку груп працівника через проміжну таблицю employee_groups. Для демонстрації підготовлено колекцію Postman.

## 11. Що скрінити для звіту

Після виконання на своєму комп’ютері зроби скріни:

1. Структура папок проєкту в редакторі.
2. GET `/api/health`: URL, код 200 і відповідь про підключення.
3. GET `/api/children`: список дітей.
4. POST `/api/children`: тіло запиту й створений запис із кодом 201.
5. PUT створеної дитини: JSON і оновлена відповідь 200.
6. DELETE створеної дитини: код 204; повторний GET — 404.
7. GET `/api/kindergartens/1/child_groups`: перевірка 1:M.
8. GET `/api/employees/1/groups`: перевірка M:M.
9. GET `/api/relations/employees_groups`: працівники з вкладеними групами.
10. Загальний результат Run collection у Postman.
11. Сторінка репозиторію GitHub після завантаження коду.

На скріні Postman мають бути видимі метод, URL, код відповіді та JSON; для POST/PUT також Body запиту. Звіт з реальними результатами можна завершити після цих запусків.
